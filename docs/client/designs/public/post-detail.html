React Server Components 실전 가이드 - 서버와 클라이언트의 경계를 설계하는 방법

#React #RSC #Next.js #Architecture #Performance

소개

React Server Components(RSC)가 Next.js App Router에 정식 도입되면서, 프론트엔드 아키텍처의 패러다임이 바뀌고 있습니다. 하지만 "서버 컴포넌트는 서버에서 실행되고, 클라이언트 컴포넌트는 브라우저에서 실행된다"는 단순한 이해만으로는 실전에서 마주치는 수많은 설계 결정을 내리기 어렵습니다.

이 글에서는 RSC를 실제 프로덕션 환경에서 활용할 때 필요한 판단 기준과 설계 패턴을 정리합니다.

이 글은 Next.js 15 App Router 기준으로 작성되었습니다. Pages Router에서는 적용 방식이 다를 수 있습니다.

RSC란 무엇인가

React Server Components는 서버에서만 실행되는 React 컴포넌트입니다. 번들에 포함되지 않으며, 서버에서 렌더링된 결과만 클라이언트로 전달됩니다.

서버와 클라이언트의 경계

가장 중요한 설계 결정은 어디에서 서버와 클라이언트의 경계를 나눌 것인가입니다. 이 경계는 "use client" 지시어로 명시합니다.

typescript 
// 서버 컴포넌트 (기본값)
async function PostPage({ params }: Props) {
  const post = await fetchPost(params.slug);

  return (
    <article>
      <h1>{post.title}</h1>
      <PostContent html={post.html} />
      <LikeButton postId={post.id} />  {/* 클라이언트 */}
    </article>
  );
}

데이터 페칭 패턴

서버 컴포넌트에서는 async/await를 직접 사용하여 데이터를 가져올 수 있습니다. 기존의 getServerSideProps나 useEffect 패턴은 더 이상 필요하지 않습니다.

직렬 vs 병렬 페칭

여러 데이터 소스를 가져올 때는 직렬/병렬 여부를 신중하게 선택해야 합니다.

typescript 
// 병렬 페칭 (권장)
const [post, comments, related] = await Promise.all([
  fetchPost(slug),
  fetchComments(postId),
  fetchRelated(postId),
]);

워터폴 방지

부모 컴포넌트의 데이터 페칭이 완료된 후에야 자식 컴포넌트의 페칭이 시작되는 워터폴 패턴을 피해야 합니다. Suspense와 병렬 페칭을 조합하면 이를 해결할 수 있습니다.

패턴 장점 단점 적합한 상황
직렬 페칭 단순함 느림 (워터폴) 의존 데이터
Promise.all 빠름 전체 실패 가능 독립 데이터
Promise.allSettled 부분 성공 가능 에러 처리 복잡 선택적 데이터

컴포넌트 트리 설계

RSC의 핵심은 컴포넌트 트리에서 서버/클라이언트 경계를 어떻게 나눌지 결정하는 것입니다. 다음 원칙을 따르면 대부분의 상황에서 올바른 판단을 내릴 수 있습니다:

  • 서버 컴포넌트를 가능한 한 높이 배치한다
  • "use client" 경계를 가능한 한 낮게 내린다
  • 상태와 이벤트가 필요한 최소 단위만 클라이언트로 분리한다
  • 데이터 페칭은 서버 컴포넌트에서, 렌더링 로직은 props로 전달한다

실전 리팩토링 사례

기존 Pages Router 프로젝트를 App Router로 마이그레이션하면서 적용한 체크리스트입니다:

  • getServerSideProps를 서버 컴포넌트 async 함수로 전환
  • useEffect 데이터 페칭을 서버 컴포넌트로 이동
  • 전역 상태(Zustand)를 필요한 컴포넌트에만 적용
  • 라우트 핸들러 API 정리 (진행 중)

성능 측정

RSC 도입 전후의 성능 변화를 측정한 결과입니다. JavaScript 번들 크기가 34% 감소했고, LCP(Largest Contentful Paint)가 평균 1.2초에서 0.7초로 개선되었습니다.

주의사항

RSC를 도입할 때 주의해야 할 점들을 정리합니다:

  1. 서버 컴포넌트에서 브라우저 API(window, document)를 사용할 수 없습니다
  2. 서버 컴포넌트에서 클라이언트 컴포넌트로 전달하는 props는 직렬화 가능해야 합니다 (함수, Date 등 불가)
  3. Third-party 라이브러리 호환성을 반드시 확인해야 합니다

결론

React Server Components는 단순히 "서버에서 렌더링한다"는 것 이상의 의미를 가집니다. 컴포넌트 트리의 각 노드가 어디에서 실행되어야 하는지를 의도적으로 설계하는 새로운 사고 방식입니다.

핵심은 서버/클라이언트 경계를 최대한 낮게 내리고, 데이터는 서버에서, 인터랙션은 클라이언트에서 처리하는 것입니다. 이 원칙만 지키면 번들 크기 감소와 성능 향상을 자연스럽게 얻을 수 있습니다.
